# 项目检查与优化方案

检查日期：2026-10-27。代码基线：`c94871e`。范围：Python 采集与计算、全部发布接口、D1 查询、前端主要功能、工作流和现有测试。

后续实施状态见 [优化实施记录与上线说明](optimization-implementation-2026-10-27.md)。本文件保留改造前的问题与计划，末尾的基线测试数量不代表改造后的结果。

这是一份改造方案，不代表下述问题已经修复。没有访问生产数据库、修改生产配置或部署。资源超限的具体类别、线上部署版本和套餐仍需通过 Cloudflare 日志确认。

## 1. 结论与边界

保留 React + Worker + D1 + GitHub Actions + R2 的总体分工。重计算在 Python 中完成，Worker 提供有界的数据接收和查询；当前没有证据证明必须迁移整套技术栈。

主要问题不是单个 timeout 太短，而是：

1. 发布的工作量没有真正限制到每个 HTTP 请求内。
2. 发布任务、数据版本、实时行情共用可变 latest 表，失败和并发会影响读者。
3. 成功状态只反映部分过程，没有严格代表数据完整、及时和可用。
4. 收益、日期、复权、推荐基准等领域含义没有贯穿采集、数据库和 UI。
5. 测试能证明部分函数行为正确，但没有覆盖跨请求恢复、真实 SQL 和用户流程。

证据等级：**确认**表示代码明确存在；**复现**表示本地最小案例已验证；**待测**表示风险成立但生产发生概率和成本需要测量。不能把待测项称为已发生事故。

## 3. 目标数据流

```text
数据源 → 采集、标准化 → 校验覆盖率和时间 → Python 因子计算
                                    ↓
                         R2 保存不可变产物和 manifest
                                    ↓
                      创建发布任务 → 小批上传 → 校验齐全
                                    ↓
                         原子切换 active_snapshot_id
                                    ↓
                         Worker 查询 → React 页面

实时行情 → 校验源时间 → 小批条件更新 quotes_latest
用户自选/策略 → 独立用户数据表
```

日线因子、实时行情、财务、行业资金的更新节奏不同。分别记录版本和时间，查询响应明确返回各自的新鲜度；不强行用一个“更新时间”代表全部数据。

## 4. 发布协议设计

建议引入带版本的新协议，分为 begin、chunk、status、commit 四类操作。不要先大规模移动代码再设计协议。

### 任务与批次

- begin：提交数据集、schemaVersion、runId、数据日期、预期行数/批次数、输入产物摘要和发布类型。
- chunk：携带 runId、chunkIndex、批次内容及摘要；每次只处理本批，服务端重新计算本批摘要并校验，不信任客户端给出的摘要。
- status：小响应返回已接受批次或连续进度，恢复时不重发整个市场。
- commit：检查全部批次、唯一行数、数据集质量门槛和版本竞争条件，再切换生效版本。
- 同 runId、同 chunkIndex、同内容重复发送返回既有结果；同编号不同内容返回冲突。
- 传输超时后先查进度；成功响应丢失不应重复计数。1102 等明确不可重试错误保留产物与诊断信息，停止无效循环。

### 数据结构建议

- `dataset_runs`：数据集、任务、schemaVersion、状态、预期和已接受行数、产物摘要、数据日期、开始/完成时间、错误分类。
- `dataset_chunks`：任务、批次编号、摘要、行数、接受时间；任务和批次编号组合唯一。
- `dataset_active`：每个数据集的当前生效版本及版本序号。
- `screen_snapshot_rows`：snapshot_id + code 组合主键，保留筛选所需的类型化字段。
- `quotes_latest`：标的、报价、源日期/时间、来源和接收时间。
- 稳定的标的主表：承接用户自选等外键；不随快照清理删除。

当前 `stock_latest` 被多个表外键引用，不能简单删表或在每次发布时清空。迁移应先新增结构、回填旧数据，再切换读写路径。

### 一致性规则

1. 批次数据与批次接受记录在同一事务边界提交，避免“数据写了但计数没写”或相反。
2. 最终提交仅更新少量元数据和生效指针，不在 commit 时复制整个市场。
3. 旧任务即使较晚完成，也不能覆盖已经生效的更新数据；采用数据日期和条件更新版本序号共同约束。
4. supplemental_st 和 single_stock 采用单独补充层，或合并成完整候选版本；不能把其局部内容切换为全市场。
5. 每行 code 唯一，行日期与任务声明一致或有明确例外；重复代码不能充当覆盖率。
6. 总体行情可接受逐标的更新，但单标的时间必须单调；如果产品要求行情全量一致，也用独立行情版本。
7. 同一日线分页会话应固定 snapshot_id，避免翻页过程中版本切换导致漏行或重复。

### 资源预算

同时限制批次字节数、行数、SQL 数量和可变字符串长度。先以小批做基准测试，再选批次大小；不要把“100 条”当作平台安全值。数据库元数据操作也计入请求工作量。

需要记录每请求的字节数、接受行数、SQL 数量、数据库耗时及平台 CPU/内存结果。客户端 wall time 不能替代 CPU 时间。Workers 免费计划每次 HTTP 请求 CPU 限额为 10ms，内存为每 isolate 128MB；套餐和实际错误类型需要线上确认。参见 [Cloudflare limits](https://developers.cloudflare.com/workers/platform/limits/)。

付费 CPU 配额可以增加运行余量，但不会修复半发布、乱序覆盖和错误收益展示。升级是否必要应根据基准数据决定。

## 5. 数据与指标契约

### 单位与时间

建立唯一字段定义，至少包含名称、类型、单位、可空性、来源、计算版本和日期含义。前端展示、规则条件、CSV、Python 与 Worker 校验使用相同定义。

建议明确：ret20d 等收益比值使用 0.1 表示 10%；日涨跌幅若继续使用 10 表示 10%，字段描述必须明确；跟踪收益不要复用 ret20d。金额明确币种与单位。源报价时间、日线因子日期、财报报告期、公告日和系统接收时间分别保存。

对来源字符串日期严格标准化，并以交易日历和市场时区判断时效。MAX(updated_at) 只能表示“至少一行最近更新过”，不能作为数据集完成证明。

### 历史与评分

- 前复权增量需要检测重叠区间的价格变化，变化时重抓受影响历史；更长期可保存原始价与复权因子。
- 技术计算可只读取最新计算所需窗口，但需保留最长指标及其预热期。不能直接截断为 250 行而忽略斜率、波动等额外窗口要求。
- 当前趋势和动量是同日横截面排名，必须在完整目标集合的最新因子汇总后计算，不能按上传批次分别排名。
- 股票和 ETF 是否共享评分池应由产品口径明确；过期交易日、停牌、次新股分别标记，不能悄悄与新数据混为一组。
- 对不足窗口的数据返回 unavailable，而不是用更少数据模拟完整指标。避免缺失多数因子却凭少量高分进入 Top10。

### 推荐与自选

推荐快照必须冻结 code、排名、评分、规则/计算版本、产生时间、参考报价及其时间。重复发布不得改写已经展示的基准。没有快照时只展示当前候选，跟踪收益为空。

价格收益与包含分红、拆分处理的总收益不是同一指标。第一阶段明确显示价格收益与报价时间；如要支持长期跟踪，再增加公司行动处理与一致基准。

### 财务

合并后统一将非有限值与缺失值转换为合法空值，并按字段校验。选取逐股票最新已披露记录；部分字段缺失不能无条件覆盖同报告期已有有效值，需定义数据源修订与更新规则。报告期不同可以合理共存，但应被明确展示，不能简单标记成同一季完整覆盖。

## 6. 查询和前端

- 规则依赖检查从 find 改为去重后的完整依赖集合。能力返回覆盖率和有效日期，而非一个 EXISTS 布尔值。
- 按实际规则构造必要 JOIN；排序/过滤仍使用白名单和参数绑定，保留现有防注入方式。
- 先检查 EXPLAIN QUERY PLAN 和 rows_read，再设计索引。不要给每个因子加索引，避免写放大。
- 版本固定的总览、Top10 可在 Python 或提交阶段的小规模步骤预生成；缓存键带版本号。实时行情参与的响应需要独立 TTL/版本。
- 任何缓存都不混用用户身份；自选、策略和会话响应不能落入公共数据缓存。
- 对普通列表保持分页。规则结果目前固定读取第一页 100 条，应提供分页或清晰注明只显示前 100 条；导出明确当前页还是全部。
- 提供统一 API 错误类型，包括 HTTP 状态、错误代码、是否可重试和请求 ID；不要将所有错误显示为 Request failed。
- 按当前页面加载数据，公共请求去重；筛选用取消或请求序号保护，避免过期结果覆盖。
- 只在任务活跃时轮询刷新状态，终态后停止并重载相关数据；页面不可见时降低频率。
- 身份请求 401 才清除登录态；自选 500 或网络故障保留登录态和旧列表并显示错误。
- CSV 独立定义自选收益列，处理百分比转换、引号转义和导出范围，释放临时对象 URL。
- 北交所市场链接应使用真实 market 字段，不能简单把非沪市全归为深市。

鉴权代码已有密码派生、会话签名和用户隔离，宜保留。补充登录频率限制、会话失效策略与线上耗时测量；不通过降低密码保护强度解决性能问题。

## 7. 工作流、恢复与观测

历史数据更新后先验证并保存不可变 R2 对象及 manifest，成功后更新历史 current 指针。发布包作为独立产物保存；发布失败后可从相同产物恢复，不重新采集生成新的 runId。

R2 中的历史 current 指针和 D1 中的当前发布版本是两个独立状态，不要求跨系统事务；分别记录其成功状态与关联产物，让恢复流程明确。

辅助数据失败可以不阻塞核心筛选，但工作流汇总应显示 partial，页面显示相应数据的新鲜度；不能只有日志 warning。增加交易日判断和单步骤/整体超时。

跨工作流共享数据时采用数据库条件更新和租约保证正确性，CI concurrency 仅用于减少冲突，不能充当唯一一致性保障。刷新状态允许 queued → running → completed/failed/expired，拒绝迟到回调将终态改回 running。

增加结构化日志：requestId、runId、dataset、chunkIndex、payloadBytes、rowCount、duration、errorCode、已确认进度。保留 Cloudflare Ray ID，禁止记录发布密钥、令牌和完整敏感配置。

健康检查区分服务存活与数据就绪；可用性判断来自各数据集的版本、日期和覆盖率。

## 8. 代码组织

在修复协议和行为时逐步拆分，而非单独做一次大规模搬文件：

```text
worker/src/
  routes/       # screener、publish、refresh、auth、watchlist
  services/     # 发布状态机、数据质量、推荐快照
  repositories/ # 类型化 SQL 与事务边界
  schemas/      # 请求、批次和领域字段
frontend/src/
  features/     # screener、rules、recommendations、watchlist、refresh
  hooks/        # 数据加载、任务轮询
  lib/          # API 错误、格式化、CSV
pipeline/
  publishing/   # 统一传输、幂等、续传
  validation/   # 字段标准化、覆盖率、时效
  jobs/         # 参数解析和任务编排
```

只抽取真正共享的传输和状态机制；资金、财务、行情仍保留各自的数据语义与更新规则。Python 已有 uv.lock，但工作流用 pip install -e .，应使用与锁文件一致的可复现安装方式。

## 9. 分阶段实施与验收

### 第一批：建立事实与修复独立缺陷

修复详情参数、财务空值、收益单位、回撤、推荐伪跟踪、规则依赖与刷新轮询。加入相应回归测试，同时采集现有发布的线上 CPU、payload 和错误类型基线。

验收：详情链接可打开；财务不匹配集合可导出；最新 60 日价格恒定时回撤为 0；没有推荐基准时不显示跟踪收益；多数据集规则明确指出缺失项；任务结束后按钮和数据恢复。

### 第二批：发布协议与数据版本

先完成新增表及兼容迁移，再实现筛选的 begin/chunk/status/commit 和 Python 发布器，验证完成后复用于其他数据集。行情独立更新并增加时间保护。

验收：

1. 6000 行、多批实际通过；每个请求数据量受限，没有全市场重复解析。
2. 任意批次中断、重复、响应丢失后恢复，内容和行数一致。
3. 相同批号不同内容被拒绝；缺批、重复代码、低覆盖率不能 commit。
4. 发布期间普通筛选、总览和 Top10 始终读完整旧版或完整新版。
5. 较旧任务晚完成不回滚新版本；旧行情晚到不覆盖新行情。
6. supplemental_st/single_stock 不替换全市场。
7. 生产代表性负载下 CPU 有可测余量；本地 wall time 不作为通过依据。

### 第三批：流水线与数据口径

保存产物后独立发布；补充覆盖率、交易日、复权变化恢复、逐股票财报选择、推荐快照写入及 schema/计算版本。

验收：仅重跑发布即可恢复；采集大面积失败时旧版本继续服务；历史复权调整不会拼接出价格跳变；价格与日期、收益与基准可追溯。

### 第四批：按测量优化成本

预计算、缓存、查询索引、按需 JOIN、Parquet 读取下推、增量计算及过期数据清理。维护改造前后 payload、CPU、rows_read/rows_written、任务耗时和失败率对照。

验收：指标改善且结果与基线等价；无新增用户态缓存泄露、数据过期或写放大问题。

### 发布次序

兼容性新增 migration → 新协议 Worker → Python 客户端 → 验证新数据完整 → 切换读路径 → 观察稳定性 → 停用旧协议 → 小批清理旧版本。正式部署前以实际迁移和回滚方案为准，不把删除旧列/表混入首轮上线。
